# upupt 信封改造手册

> 当前预置画像速查（端口/算法/槽位/密钥路径）：[信封画像一览.md](./信封画像一览.md) · [信封画像.json](./信封画像.json)

这份手册只讲一件事：在现有进程上加六类信封，让调用方用头、query、表单或 JSON 把参数送进来，验过之后得到一份固定形状的假数据，再按原来的槽位封回去。

不新增业务 method。不按渠道编出险、证件、保单这类结果。现有九个接入面和三个 method 的行为保持原样。

读这份手册的人应该能直接改代码。下面写到的文件、函数、配置键、失败原因，都按现在仓库里的结构落点。改的时候以离被改文件最近的规则为准。配置解析已经是 `deny_unknown_fields`，新键必须同时加进结构体和 `config/app.toml`，漏一边进程起不来。

## 改完之后

一个进程，十五个接入面都常开。原来的九面仍听 `3000` 到 `3008`。新的六面听 `3010` 到 `3015`。六面之间不共用 Router，不共用票桶，也不把请求转给 `core::dispatch`。

| 面 | 端口 | 类 |
|---|---|---|
| `envelope_token_plain` | 3010 | 换票，业务体明文 |
| `envelope_token_crypt` | 3011 | 换票，业务体加密 |
| `envelope_sign_plain` | 3012 | 每次签名，业务体还能读 |
| `envelope_sign_crypt` | 3013 | 每次签名，业务体加密 |
| `envelope_cred_plain` | 3014 | 凭据附在报文上，业务体明文 |
| `envelope_cred_crypt` | 3015 | 凭据附在报文上，业务体加密 |

国密不单开面。SM3 只签名，落在 `envelope_sign_plain`。SM4 整包、SM2 包 SM4、HMAC-SM3，落在带 `crypt` 的那三个面里，和 AES、DES、RSA 一样，靠画像选择算法。

`enabled` 只有接入面这一层，和现有九面同一个字段，默认 `true`。画像没有第二套开关。写进配置里的画像就是活的。不想要某一种算法，删掉那条画像，不要写成 `enabled = false`。

## 六类各自认什么

六类是两根轴的组合。第一根是怎么认调用方：换票、每次签名、凭据附在报文上。第二根是业务体打不打开：明文，或者加密。六种组合在现场报文里都出现过，所以是六类，不是把加密当成可有可无的附加。

换票的两个面各有两条路。一条发牌，一条用牌调业务。发牌只回票，不生成业务假数据。用牌的那条先查本面票桶，再处理业务体。

签名的两个面每次都验签。明文面验完就能读业务字段。加密面先验签，再解密，顺序写在画像的 `order` 里，因为有的报文是先签名再加密，有的是先加密再签名。

凭据的两个面不发牌，也不验签。头、query 或体里的凭据字段和配置比对。加密面在凭据通过之后再解密。

头和体不是类。同一个请求可以头上放票、体里放业务，也可以签名在 query、密文在体里。位置写在画像的槽位上。

## 槽位

一个字段只有四个槽位：`header`、`query`、`form`、`json`。

收参时四个槽位都扫，但只有画像点了名的字段才进表。没点名的头丢掉，包括调用方自己带的 `userid`、`X-Trace-Id`、`X-Request-Id`。`X-Request-Id` 仍按现有规则当流水号，不进业务表。

一张表分三格：

- `auth`：票、签名、凭据、包装密钥。验完就从业务格拿走。
- `cipher`：还没解开的密文，或者解开后要并回去的内层字段。
- `biz`：剩下的业务字段。模拟数据只看这一格。

同名冲突按画像的 `slot_priority` 决定留谁。没写的话顺序是 `json`、`form`、`query`、`header`，前者覆盖后者。不要默默合并成数组。

表单和 query 的值一律是字符串。不要走 `src/front/util.rs` 里的 `coerce_field` 或 `query_to_biz`。那两个函数是给三个 method 用的，会把 `"1"` 收成数字。信封这边保持原样，同样的字节永远得到同样的假数据。

JSON 数字保留报文里的词法形式，不改成浮点再打印。`null` 留着。数组保持顺序。布尔就是布尔。

### 编码不是加密

`body_kind` 决定体怎么读：

- `json`：`Content-Type` 必须是 `application/json`。带了 charset 就必须是 `utf-8`，别的字符集直接 `bad_shape`。
- `form`：`application/x-www-form-urlencoded`。
- `raw`：体是一整段字节，不当 JSON 解析。密文整包、Base64 整包走这里。
- `empty`：体必须是空的。字段只来自头或 query。体不空就是 `bad_shape`。

`body_encoding` 只有 `identity` 和 `base64`。Base64 是编码，先解开再交给 `body_kind`。它不是 AES，也不是 SM4。

体上限写死 1 MiB，放在 `src/envelope/slots.rs` 的常量里，不进配置。超出回 HTTP 413，原因 `bad_shape`。这是传输限制，不是业务分支。

### 现场出现过的槽位组合

这些组合都要能配出来。名字是画像模板，不是业务接口。

换票，体明文：

- 发牌在表单的 `username`、`password`。用牌时票在头 `Authorization`，前缀按画像原文匹配，有的是 `bearer `，有的是 `Bearer `。业务在表单。
- 发牌在 query 的 `clientId`、`clientSecret`，GET。用牌时票在 JSON 字段 `accessToken`，不在头上。业务也在这个 JSON 里。

换票，体加密：

- 发牌在 JSON 的 `corpId`、`corpSecret`。用牌时票在头 `Authorization`，前缀 `Bearer `。业务 JSON 先签名，再整包 SM4，密文放在体里的一个字段，或整个 raw 体。画像用 `order` 写明是先签再加密。

每次签名，体还能读：

- 签名在 JSON 字段 `sign`。拼串规则各写各的，见下面的 `canon`。
- 签名在头 `sign`，旁边还有 `secret-id`、`ts`、`trace-id`、`sign-type`。业务是 JSON 体。
- 签名在 JSON 或表单，算法是 HMAC-SHA256，体是表单，字段还能读。
- 签名在 JSON 字段，算法是 SM3，体是 JSON，字段还能读。

每次签名，体加密：

- 头上有 `Authorization`，值是 `Basic ` 加上一段自定义原文的 Base64，不是 HTTP Basic 的 `user:pass`。体里有被 RSA 公钥包起来的 AES 密钥，和 AES-CFB 密文。
- 签名和密文都在 JSON 里。对称算法是 AES，摘要是 MD5。
- 业务体被 RSA 私钥加密后放进 JSON 的 `biz_content`，外面再做 SHA256WithRSA。这是私钥加密，不是公钥加密。
- 签名是 MD5。密文在 query 的 `params`，算法 AES-GCM。体是空的，哪怕 `Content-Type` 写了 JSON。
- 明文里先放 MD5，再整包 SM4。没有票。
- 部分字段 SM4，输出是 hex。签名在 query 的 `sign`，旁边有 `appKey` 和 `version`。体是 Base64 之后的 JSON，先做 `body_encoding = base64`，再解析 JSON。
- 体是 JSON。用户标识字段用 SM4-CBC 加密。签名是 HMAC-SM3，材料里带 `sign_factor`。
- SM2 加密加 SM2 签名，结果放在 JSON 字段里。这是标准算法，画像写明 user id 和模式。
- 凭据不在这一类。这一类必须有签名槽。

凭据附在报文上，体明文：

- 用户名和密码在 JSON 体里。没有签名。
- 凭据在头 `AppCode`，方法标识在头 `pcode`。业务在 JSON 体。
- GET。凭据 `company_id` 和业务字段都在 query。

凭据附在报文上，体加密：

- 表单里有 `username`、`apiKey`、`format`，`params` 是 DES/CBC 密文。响应是明文 JSON。画像的响应槽位可以和请求不一样，这里响应就是 `json`，不再加密。

一个面可以挂多条画像，用方法加路径区分。同一个面里两条画像的方法加路径重复，启动失败。路径必须以 `/` 开头。没有画像点到的路径回 404。不允许写一个吞掉所有路径的兜底路由。

画像的 `methods` 只能是 `GET` 和 `POST`。别的方法回 405。不提供 CONNECT 和 TRACE。

## 一次请求怎么走

六面共用 `src/envelope/pipeline.rs`。差别只在画像。

1. 用方法和路径选画像。选不中，404。
2. 读体，超过 1 MiB 就 413。
3. 按 `body_kind` 和 `body_encoding` 把体解开。形状不对，`bad_shape`。
4. 按槽位收成表。缺了画像要求的字段，`bad_shape`。
5. 睡一段 `[latency]` 里的时间。调用现有接入面进业务之前用的那个 sleep，不要在信封面另写随机范围。
6. 认调用方。
   - 换票的业务路：从票槽取出串，去掉画像写明的前缀，到本面票桶里查。查不到是 `bad_token`。
   - 签名路：按 `canon` 拼材料，用画像的算法算，和签名槽比对。不对是 `bad_sign`。有时间戳字段就用现有 `[sign].window_seconds`。有 nonce 字段就用本面自己的 nonce 表，TTL 用 `[sign].nonce_ttl_seconds`。
   - 凭据路：每个凭据字段和配置做定长比较。长度不同或内容不同都是 `bad_credential`。
7. 这一步如果画像有加密，按 `order` 插进来。`sign_then_encrypt` 是先验签再解密。`encrypt_then_sign` 是先解密再验签。解开失败是 `bad_decrypt`。解开得到的 JSON 对象并进 `biz`。内层如果还有签名字段，验完从 `biz` 拿走。
8. 从 `biz` 里删掉仍然留着的票、签名、凭据、密钥字段。
9. 用 `biz` 生成假数据。
10. 按响应槽位封回去。需要加密就加密，需要签名就签名。`order` 反过来用：请求是先签再加密，响应就是先签名再加密。

发牌路不走第 7 到第 9 步。凭据或账密通过之后，发一枚本面票，按画像的响应字段名放回去。票的有效期用 `[token].expire_minutes`。

## 模拟数据

假数据不调用 `core::dispatch`，也不读帖子、图片、比对这三个 method。渠道报文里没有 `keyword`、`user_id` 这些入参，解开了也搜不了帖。

三个 method 留在原来九面。信封面的出参是下面这个对象，字段就这些，多一个少一个都算实现错误。

```json
{
  "ok": true,
  "reason": "",
  "hit": true,
  "fields": {},
  "digest": ""
}
```

`fields` 是 `biz` 的原样拷贝。`hit` 在 `biz` 至少有一个字段时为 `true`，否则为 `false`，这时 `fields` 是 `{}`。

`digest` 是 `biz` 的规范 JSON 的 SHA-256，十六进制小写。规范 JSON 的规则：

- 对象的键按 UTF-8 字节序排序。
- 不要无意义的空白。
- 字符串按 JSON 转义。
- 数字用收进来时的词法形式。
- `null`、`true`、`false` 保持原样。
- 数组不排序。

空对象的规范形式是 `{}`。同样的 `biz` 必须得到同样的 `digest`。`digest` 不算进自己，只覆盖 `biz`。

失败时如果还能放进信封，对象改成：

```json
{
  "ok": false,
  "reason": "bad_sign",
  "hit": false,
  "fields": {},
  "digest": ""
}
```

`reason` 只允许：`bad_token`、`bad_sign`、`bad_credential`、`bad_decrypt`、`bad_shape`。成功时 `reason` 是空串。

没有档案可查这件事，就用 `hit = false` 表达。不要另造查无、参数错、收费这套渠道码。

## 失败放哪

画像有 `fail_in`，取值 `http` 或 `envelope`。

`http`：不包信封。`bad_token`、`bad_sign`、`bad_credential` 回 401。`bad_decrypt` 和 `bad_shape` 回 400。体是上面的失败对象，明文。

`envelope`：HTTP 仍是 200，失败对象按响应槽位加密或签名之后放回去。调用方解开才能看见 `reason`。

有一种情况不能包信封：密钥还没解开，或者解密用的材料缺失。这时即便画像写了 `envelope`，也回 HTTP 401 或 400，体是明文失败对象。日志里的 `error` 写实际原因，不要写成成功。

发牌失败同样走 `fail_in`。发牌成功的体只有画像点名的字段，例如 `token` 或 `accessToken`，外加 `expires_in`（秒）。不要塞 `hit` 和 `digest`。

## 算法

算法是闭集。画像写了集外的名字，启动失败。集内每种算法都要有往返测试，不能只把名字接上。

摘要和签名：

- `md5`。输出 hex。`hex_case` 为 `upper` 或 `lower`。
- `hmac_sha256`。密钥来自文件。输出按画像选 hex 或 base64。
- `sm3`。对画像给出的材料做 SM3，输出 hex。
- `hmac_sm3`。输出按画像选 raw 的 base64，或 hex。比较用定长比较。
- `rsa_sha256`。对材料做 SHA256WithRSA，输出 base64。填充用 PKCS#1 v1.5。
- `sm2_sign`。SM2 签名。`user_id` 必须写在画像里。本仓库自带的默认画像用 `1234567812345678`，别的调用方有自己的 user id 就写自己的，不要在代码里写死。

对称加密：

- `aes_ecb_pkcs5`。对应 Java `Cipher.getInstance("AES")` 和 Hutool `SecureUtil.aes`。密钥 16、24 或 32 字节。
- `aes_cfb`。必须同时写 `padding`（`none` 或 `pkcs5`）、`segment_bits`、`iv_from`。`iv_from` 可以是 `key`、`random_prefix`、`field`。不写就启动失败。不要猜 CFB 的填充。
- `aes_gcm`。必须写 `iv_len` 和 `tag_bits`。自带默认画像用 12 和 128，这只是默认画像的值，不是算法唯一合法值。
- `des_cbc_pkcs5`。密钥 8 字节，IV 8 字节。`iv_from` 必填。
- `sm4_ecb_pkcs7`。对应 Hutool `SmUtil.sm4`。密钥 16 字节。分组 16 字节时 PKCS5 和 PKCS7 是同一件事，代码里只用 PKCS7 这个名字。
- `sm4_cbc_pkcs7`。密钥 16 字节，IV 16 字节，`iv_from` 必填。
- `sm4_ecb_nopadding`。输入长度必须是 16 的倍数，否则 `bad_decrypt`。

非对称加密：

- `rsa_pkcs1_public`。公钥加密，私钥解密。用来包对称密钥。
- `rsa_pkcs1_private`。私钥加密，公钥解密。用来直接加密业务体。不要和上一档混用。
- `sm2_encrypt`。SM2 加密。模式写在画像里，自带默认画像用 C1C3C2。

输出编码是另一项：`hex`、`base64`、`base64_upper_hex` 不存在。hex 的大小写跟 `hex_case`。整包密文和字段密文用同一个算法，差别只是 `cipher_scope`：`body` 或 `fields`。`fields` 必须列出字段名。

密钥包装：画像可以写 `wrap = rsa_pkcs1_public` 或 `wrap = sm2_encrypt`。请求里的对称密钥先解包，只用于这一次。响应另生成一把对称密钥，用同一套包装放进响应槽位。没有 `wrap` 就是预共享密钥，请求和响应用同一把。

`order` 只有 `sign_then_encrypt` 和 `encrypt_then_sign`。明文面不写 `order`。

拼串规则 `canon` 也是闭集：

- `sorted_kv`：键排序，跳过画像列出的名字（至少跳过签名字段自己），用配置的分隔符连接。可以在前面或后面拼一段密钥。
- `concat`：按画像给出的字段顺序拼接，分隔符可空。可以在两头拼密钥。
- `raw`：取一个槽位的原始字符串，两头可以拼密钥。

这三档覆盖现场的 MD5 拼法：密钥和材料用 `&` 连，材料后面直接接密钥，或者若干头、体、时间戳按固定顺序接密钥。新拼法先加枚举和测试，再给画像用。不要在匹配分支里临时拼。

## 画像配置

六面的公共监听字段和现有面一样：`enabled`、`host`、`port`、`http2`、`h2c`、`tls`。`auth` 固定写成空数组。信封不走 `AuthMethod`。不要把这六面塞进 `oauth_cc`、`api_key`、`hmac` 那套枚举。

每个面下面是 `[[fronts.<面>.profiles]]`。一条画像的字段如下。没用到的字段不要出现，因为结构体是 `deny_unknown_fields`，可选字段用 `Option`，缺省在代码里解释，不靠注释掉的键。

- `name`：面内唯一。
- `kind`：`issue` 或 `call`。换票面两种都有。另外四个面只有 `call`。
- `methods`：`GET`、`POST` 的非空列表。
- `path`：以 `/` 开头，面内方法加路径唯一。
- `body_kind`：`json`、`form`、`raw`、`empty`。
- `body_encoding`：`identity` 或 `base64`。
- `slot_priority`：可选，四个槽位的排列。
- `fields`：数组。每项有 `name`、`slot`、`role`。`role` 是 `auth`、`cipher`、`biz`、`sign`、`token`、`wrap_key`、`timestamp`、`nonce`。`biz` 可以不逐个点名，用 `biz = rest` 表示其余字段都算业务。点了名的 auth 字段不会漏进 `rest`。
- `token_prefix`：仅票在头上时必填。按原文匹配，包括大小写和末尾空格。
- `token_response_field`：发牌响应用这个字段名。
- `secrets`：凭据或发牌账密的文件路径。文件内容是一行，比较时去掉末尾换行。
- `canon`、`canon_skip`、`canon_sep`、`canon_prefix_key`、`canon_suffix_key`、`canon_fields`。
- `sign_alg`、`hex_case`、`sign_encoding`。
- `crypt_alg`、`cipher_scope`、`cipher_fields`、`crypt_encoding`、`padding`、`segment_bits`、`iv_len`、`iv_from`、`tag_bits`、`user_id`、`sm2_mode`。
- `key`、`private_key`、`public_key`：文件路径，相对可执行文件目录，和现有 `rsa_public_pem` 的解析方式一样。
- `wrap`：不包装就别写。
- `order`。
- `fail_in`。
- `response_body_kind`、`response_encoding`、`response_slots`。不写就和请求一样。DES 那档请求加密、响应明文，就是靠响应槽位写成 `json` 且不写 `crypt_alg` 的响应侧。实现上请求算法和响应算法分开：`response_crypt_alg` 缺省等于请求的 `crypt_alg`，写了 `none` 就明文回去。

启动时检查：

- 六个面的节都在。缺节失败。
- 启用的面至少一条画像。
- 密钥文件存在，长度符合算法。SM4 必须 16 字节。DES 必须 8 字节。AES 必须 16、24 或 32 字节。RSA 和 SM2 必须能解析。
- 两个面绑同一个 `host:port` 失败。这条沿用现有检查。
- 未知面名、未知算法、未知槽位，失败。
- 至少还有一个 `enabled = true` 的面。这条也是现有规则，不要改掉。

密钥在启动时一次读完。不要等到第一笔请求再读。

## 自带的六条默认画像

仓库里要有一套能跑通的默认画像，调用方不带渠道字段也能打这六个端口。这套画像用中性字段名，证明槽位和算法，不模仿任何一家的业务体。

`envelope_token_plain`：

- `POST /issue`，表单 `username`、`password`，回 JSON `access_token`、`expires_in`。
- `POST /call`，头 `Authorization` 前缀 `Bearer `，JSON 体里除票以外的字段算 `biz`。

`envelope_token_crypt`：

- `POST /issue`，JSON `id`、`secret`。
- `POST /call`，头 `Authorization` 前缀 `Bearer `。体是 JSON，字段 `data` 为 SM4/ECB 密文，base64。预共享 16 字节密钥。

`envelope_sign_plain`：

- `POST /call`，JSON。`sign` 为 MD5，`hex_case = lower`。`canon = sorted_kv`，跳过 `sign`，分隔符 `&`，后面接密钥。
- 再挂一条 `POST /sm3`，JSON，`sign` 为 SM3，材料是 `canon = raw` 的业务字段 `payload`。

`envelope_sign_crypt`：

- `POST /aes`，JSON。`sign` 为 HMAC-SHA256。`payload` 为 AES/ECB 密文。`order = sign_then_encrypt`。签名材料是密文原文，这样验签时还不用解密。
- `POST /sm4`，JSON。`payload` 为 SM4/CBC。IV 来自 `random_prefix`，密文前面 16 字节是 IV。签名 HMAC-SM3，`order = encrypt_then_sign`。

`envelope_cred_plain`：

- `GET /call`，query 里 `company_id` 是凭据，其余 query 字段是 `biz`。
- `POST /header`，头 `AppCode` 是凭据，JSON 体全部是 `biz`。

`envelope_cred_crypt`：

- `POST /call`，表单 `username` 是凭据，`params` 是 DES/CBC 密文。`response_crypt_alg = none`，响应是明文 JSON 假数据。

默认密钥由 `scripts/gen_envelope_keys.sh` 生成到 `config/keys/envelope/`。脚本用 `openssl` 或一段一次性的 Rust 示例都行，但密钥字节不要写进脚本源码，也不要写进手册。运行时只引用路径。


## 票

`TokenHub` 现在只给 `auth` 里含 `oauth_cc` 或 `gettoken` 的面建桶。六面的 `auth` 是空的，所以要改 `needs_token_bucket`：两个换票面也建桶。桶仍然按 `FrontName` 分开。`3010` 发出的票，`3011` 和 `3000` 都查不到。

不要把信封的账密塞进 `[[apps]]`。`[[apps]]` 继续只给定制九面。`TokenManager::create_token` 如果必须绑定一个已登记的 app，就不要硬用它。在 `src/envelope/token_store.rs` 里做本面票表，过期时间和清理间隔仍读 `[token]`。票是随机串，至少 32 字节，URL 安全的 base64。校验失败不要区分“过期”和“没有这张票”，对外都是 `bad_token`。

nonce 表同样按面分开。现有 `src/auth/nonce.rs` 可以复用类型，不能复用同一张表。

## 日志

六面走现有 `access_log`。`front` 写新面的名字，`port` 写实际端口。`auth` 写 `envelope_token`、`envelope_sign` 或 `envelope_cred`。

`in` 记收齐之后的 `biz`，不记票、密码、密钥、签名、密文。`out` 记封回去之前的假数据对象，这样日志里看得到 `hit` 和 `digest`，而不是一段打不开的密文。密文是否生成，用现有字段表达不了的话，不要加第十六个日志列。放在 `out` 旁边会改日志格式。保持现有列不变，在 `out` 的 JSON 里加一个 `wrapped` 布尔值只属于实现草稿，不要这么做。`out` 就是假数据对象本身。

`logger::redact_query` 现在只遮 `api_key`、`x-api-key`、`access_token`、`authorization`、`secret`、`client_secret`、`image`。信封会把凭据放在 query 里，所以这份清单要加上，按小写比较：

`clientid`、`clientsecret`、`password`、`passwd`、`sign`、`params`、`encryptstr`、`appcode`、`corpsecret`、`accesstoken`、`token`。

头里的 `Authorization`、`AppCode` 不要进 `in`。现有查询脱敏继续做，上面这些键是补集。

`biz = rest` 用一个字段表示，不要做成会和 `deny_unknown_fields` 打架的自由表：

```toml
biz_rest = true
```

为真时，没有被 `fields` 点名的键都进 `biz`。为假时，只有 `role = biz` 的键进 `biz`，多出来的键是 `bad_shape`。默认画像用 `biz_rest = true`。想收紧某一条画像，把它写成 `false` 并逐个列出业务字段。

头和体同时存在时，点名即可。例如票在头、业务在体：

```toml
[[fronts.envelope_token_plain.profiles.fields]]
name = "authorization"
slot = "header"
role = "token"

[[fronts.envelope_token_plain.profiles]]
token_prefix = "Bearer "
biz_rest = true
body_kind = "json"
```

头名字在收参时按小写比较，`Authorization` 和 `authorization` 是同一个槽。前缀匹配发生在取出值之后，区分大小写。

```toml
name = "sign"

[[fronts.envelope_sign_crypt.profiles.fields]]

slot = "query"
role = "auth"
```

## 测试

先写会失败的测试，再写实现。不许改断言去迁就错误结果，也不许删掉现有 `test/acceptance.py` 里对九面的检查。

Rust 单元测试，放在对应模块底部：

- 每个算法一组往返。改一个字节必须验签失败或解密失败。
- `sorted_kv`、`concat`、`raw` 各一组，包括跳过 `sign`、大小写 hex。
- 一个请求同时带头、query、JSON。只有点名的字段进表，`X-Trace-Id` 不进表。
- 表单值 `"1"` 在 `biz` 里仍是字符串。
- 空 `biz` 的 `hit` 为假，`digest` 等于 SHA-256(`{}`)。
- 同一 `biz` 调用两次，`digest` 相同。
- 票不能跨面。
- 前缀 `bearer ` 和 `Bearer ` 互不认可。
- Base64 体先解码再进 JSON，不把它当密文。
- 体超过 1 MiB 回 413。
- 密钥长度不对时配置加载失败。
- `fail_in = envelope` 但包装密钥缺失时，回 HTTP 错误，不是 200 加一段无法解密的体。
- DES 画像请求是密文、响应是明文 JSON，响应里能直接看到 `hit`。

Python 验收放在 `test/envelope_acceptance.py`。它只打 `3010` 到 `3015` 的默认画像，不断言原来九面。每面至少一笔成功、一笔认调用方失败。加密面要在脚本里用同样的算法封一笔、解开响应，对上 `digest`。脚本自己生成临时密钥时，应请求测试进程使用的那套文件；不要在脚本里再写一套密钥。

跑法沿用仓库现有的 `cargo test`。先跑 `envelope` 过滤的那一组，再跑整套。验收脚本在进程起来之后跑。进程用 `scripts/run.sh`，密钥先用 `scripts/gen_envelope_keys.sh` 生成。

## 写的时候容易错的地方

Java 的 `Cipher.getInstance("AES")` 是 ECB 加 PKCS5，不是 CBC。把默认 AES 写成 CBC，调用方解不开。

Hutool 的 `SmUtil.sm4` 是 ECB。另有 CBC 和 NoPadding，必须由画像选择。代码里不要看到 SM4 就用 ECB。

CFB 的填充和 IV 来源不写死。画像缺这几项就拒绝启动。

RSA 有两档。包密钥用公钥加密。直接加密业务体那档是私钥加密。方向反了，往返测试会在“用公钥解密”这一步失败，不要改测试去适配反了的方向。

MD5 的 hex 有大写有小写。比较之前不要统一 `to_lowercase`，除非画像写了 `lower`。

票在 JSON 里的那档，不要去读 `Authorization`。画像没点这个头，它就不存在。

`bearer ` 和 `Bearer ` 是两个前缀。默认换票明文面用 `Bearer `。另一条画像要小写，就在那条画像里写 `bearer `。

Base64 整包不是加密。先解码，再决定还解不解密。

签名字段要排除在拼串之外。query 上的 `sign` 也一样。

响应可以比请求少一层加密。凭据加 DES 那档就是这样。不要假定响应算法永远等于请求算法。

失败对象的字段集合和成功对象一样。调用方按同一套结构解析。不要成功回 `hit`、失败回另一套 `error` 字符串。

假数据不要带渠道收费码。`hit` 和 `digest` 就是全部业务结果。

密钥、票、密码不进日志，不进手册里的示例值，不进 git。示例只写路径。
